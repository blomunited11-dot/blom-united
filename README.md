# BLOM UNITED | مجموعة بلوم المتحدة

المستودع الجديد للموقع المؤسسي لمجموعة بلوم المتحدة. يُبنى من الصفر دون استخدام كود الموقع القديم.

## الواجهة المعتمدة
- الصفحة الرئيسية تتألف من قسمين بصريين فقط: افتتاحية الهوية، ثم بطاقات قطاعات الأعمال الأربعة.
- شريط تنقل علوي ثابت في جميع الصفحات، مع قائمة قطاعات تتيح الانتقال المباشر بينها.
- بطاقات القطاعات تفتح صفحات مستقلة: المقاولات والتطوير العقاري، الصناعة، الضيافة، الخدمات الإدارية وتأسيس الأعمال.
- تصميم مؤسسي هادئ بخلفية بيضاء وهوية الشركة الرسمية، ودعم العربية والإنجليزية.
- دون فيديو افتتاحي أو أزرار إضافية في الافتتاحية.

## الصفحات الداخلية
عن المجموعة، القطاعات والخدمات، المشاريع، الأخبار والمركز الإعلامي، والتواصل.

## لوحة الإدارة
لوحة مستقلة ومحمية لإدارة الصفحات والقطاعات والخدمات والمشاريع والأخبار والوسائط والمحتوى ثنائي اللغة، مع كتالوج منتجات قابل للتوسع لقطاع الصناعة، وحسابات وصلاحيات وسجل تدقيق وحالات مسودة ونشر. التفاصيل التقنية النهائية تحتاج اعتمادًا قبل التنفيذ.

## الخدمات
- GitHub: مصدر المشروع.
- Supabase: قاعدة البيانات والمصادقة والتخزين. أفاد مالك المشروع بأنه جاهز ومربوط؛ الاتصال والأمان يحتاجان اختبارًا.
- Cloudflare: منصة النشر، والنشر متوقف مؤقتًا وفق إفادة المالك.

## ضوابط التنفيذ
- لا نقل لكود الموقع القديم.
- لا حفظ لمفاتيح سرية في المستودع العام.
- لا نشر للإنتاج دون اختبار وموافقة.
- المحتوى والصور من المواد الرسمية المعتمدة فقط.
- توثيق القرارات والتغييرات في مجلد docs/ لاحقًا.

**الحالة:** وثيقة تأسيسية فقط؛ لم يبدأ تنفيذ الموقع الجديد في هذا المستودع.

## الالتزام بالخطوط المعتمدة (إلزامي)
- تُستخدم **الخطوط الرسمية المعتمدة من مجموعة بلوم المتحدة فقط** في جميع صفحات الموقع ولوحة الإدارة، للنصوص العربية والإنجليزية، وفق دليل الهوية والملفات الأصلية المعتمدة.
- يُحافظ على رسم الشعار والكتابة المدمجة فيه كما وردت في ملفات الهوية الأصلية، دون إعادة كتابتها أو استبدال خطها أو تغيير نسبها.
- يُمنع اختيار خطوط بديلة أو خطوط نظام افتراضية أو إدخال خطوط جديدة لمجرد التحسين البصري دون موافقة صريحة من مالك المشروع.
- قبل التنفيذ، تُراجع ملفات الخطوط ودليل الهوية للتحقق من **أسماء عائلات الخطوط وأوزانها وتراخيص استخدامها**؛ لا تُفترض أسماء أو أوزان غير موثقة.
- تُطبّق الخطوط مركزيًا عبر نظام تصميم موحد مع دعم العربية والإنجليزية واتجاه RTL/LTR، وتُختبر على الكمبيوتر والجوال، مع معالجة احتياطية معتمدة فقط عند تعذر تحميل الخط.
- **معيار قبول:** لا يُعتمد أي تصميم أو صفحة أو مكوّن أو نسخة منشورة تخالف الخطوط المعتمدة.

## استقلال القطاعات وفصل المحتوى عن العرض (قرار معماري ملزم)

- القطاعات الأربعة **وحدات وظيفية مستقلة فعليًا** وليست نسخًا من صفحة واحدة تتغير فيها النصوص؛ لكل قطاع خدماته ومشاريعه وصوره ومحتواه وإمكانية إضافة خصائص خاصة به مستقبلًا.
- **المحتوى منفصل عن العرض:** تُدار النصوص والصور والخدمات والمشاريع والمنتجات عبر قاعدة بيانات Supabase ولوحة الإدارة، بينما تتولى مكونات الموقع عرض البيانات.
- يجب أن يستطيع المسؤول تغيير صور القطاعات والخدمات والمشاريع ونصوصها ونشرها من لوحة الإدارة **دون تعديل كود الصفحة أو إعادة بناء الموقع**. ويُراعى في التنفيذ أسلوب جلب البيانات وتحديثها بما يحقق ذلك؛ التغييرات البرمجية أو التفاعلات الجديدة قد تستلزم نشرًا جديدًا.
- نستخدم **نظام تصميم ومكونات وبنية مشتركة** للتنقل والهوية والخطوط والصلاحيات والوسائط، مع السماح لكل قطاع بتخطيطاته ومكوناته وتجربته الخاصة دون تكرار غير ضروري.
- تُصمم قاعدة البيانات وعلاقات المحتوى بحيث تعزل ملكية كل قطاع لمحتواه وتسمح بالتوسع، دون فرض قوالب متطابقة على القطاعات.
- معيار القبول: إدارة محتوى كل قطاع بصورة مستقلة، وتحديث المحتوى المنشور دون تعديل التصميم، مع بقاء الشريط العلوي ونظام الهوية موحدين.

## بوابة اعتماد المعمارية قبل كتابة الصفحات

**لا يبدأ تنفيذ الواجهة أو لوحة الإدارة قبل مراجعة واعتماد ما يلي:**

1. **إطار العمل والنشر:** اعتماد Next.js + TypeScript مبدئيًا، وتحديد تكامل Cloudflare Workers وإعدادات البناء والتشغيل والبيئات قبل كتابة كود الإنتاج. لا يُفترض أن إعدادات النشر القديمة صالحة.
2. **مخطط البيانات:** تعريف القطاعات (sector)، وعلاقات الخدمات والمشاريع والمنتجات والوسائط، ومحتوى اللغتين، وقيود الملكية والعلاقات والمفاتيح.
3. **الترجمة:** تحديد استراتيجية /ar و/en، وآلية تخزين المحتوى المترجم، والروابط الدائمة، وبدائل المحتوى غير المترجم.
4. **حالات النشر:** مسودة، قيد المراجعة، منشور، مؤرشف، مع قواعد انتقال واضحة ومن يملك حق الاعتماد والنشر.
5. **الأمان:** تصميم Supabase Auth وRLS على مستوى الجداول والصفوف، وفصل صلاحيات إدارة كل قطاع، وحماية وسائط التخزين وواجهات الإدارة؛ عدم الاكتفاء بإخفاء الأزرار.
6. **التحديث دون إعادة بناء:** تحديد طريقة جلب المحتوى المنشور وآلية تحديثه/إبطال التخزين المؤقت في Cloudflare، واختبار ظهور التغييرات من لوحة الإدارة دون إعادة نشر الكود.
7. **أدوار لوحة الإدارة:** اعتماد أدوار وصلاحيات مبنية على المهام ونطاق القطاع، دون افتراض وجود مدير مستقل لكل قطاع؛ يحدد المالك من يدير المحتوى ويراجعه وينشره.
8. **معايير القبول:** اختبار صلاحيات الوصول المتبادل بين القطاعات، واستقلال محتوى كل قطاع، وتبديل اللغات، وتحديث المحتوى دون نشر، ثم توثيق النتائج قبل البدء بالصفحات.

هذه **قرارات مطلوبة للاعتماد وليست تنفيذًا مكتملًا**. لا تُنشأ الجداول أو السياسات أو ملفات الواجهة قبل مراجعة المخططات واعتمادها.
